# CLAUDE.md

Firmware for an **Ulanzi TC001** desktop clock (ESP32, 32x8 WS2812 LED matrix) that shows the round
countdown timer of a tournament on [Best Coast Pairings](https://www.bestcoastpairings.com).
C++ / Arduino framework / PlatformIO. Work in progress, not released. Rewritten from an earlier
MicroPython version (see README.md).

## Working with the user

- Talk to the user in Czech; all code, comments, identifiers and log/status messages are in English.
- No flattery, no superlatives.
- Indent with 4 spaces.
- Most code is hand-written by the user; `lib/wifimgr` was largely generated by GitHub Copilot.

## Build, flash, monitor

PlatformIO CLI is not on PATH; use `~/.platformio/penv/bin/pio`.

```sh
~/.platformio/penv/bin/pio run                    # build production (env nodemcu-32s, default)
~/.platformio/penv/bin/pio run -t upload          # flash production over USB
~/.platformio/penv/bin/pio run -e dev -t upload   # flash dev build (debug output + console)
~/.platformio/penv/bin/pio device monitor -b 9600 # serial console
~/.platformio/penv/bin/pio test -e native         # unit tests on the Mac (lib/core, lib/webui)
~/.platformio/penv/bin/pio test -e nodemcu-32s    # unit tests on the TC001 (gfx, NVS, newlib time)
~/.platformio/penv/bin/python tools/bcp_contract.py <eventId>  # contract test of the live BCP API
```

- Board profile is `nodemcu-32s` (the TC001 is ESP32-WROOM based). `upload_speed = 115200`: the CH340
  USB-serial bridge is unreliable at higher rates.
- Flash usage is ~85 % of the 1.25 MB app partition (dev build ~90 %). Watch the size when adding
  features/fonts/HTML.
- Opening or closing the serial port resets the ESP32 (auto-reset circuit), even with DTR/RTS low.

### Dev build (`-e dev`, `BCP_DEV` define)
- All development code is inside `#ifdef BCP_DEV`; the production build must stay byte-identical without it.
- Debug output (`DEV_LOG("Module", msg)` from `lib/devlog/devlog.h`, printed to `Serial`) exists only in the dev
  build; in production the macro emits no code or strings.
- Serial command console (`src/devconsole.cpp`, called from `loop()`), 9600 baud, one command per line,
  each response ends with `[Console] done`. `help` lists commands: `status`, `screen` (ASCII dump of the
  matrix: `.` off, `:` dim, letters = colour), `refresh`, `mid`, `timeshift <sec>`, `beep yellow|red` (play a threshold signal),
  `fake <mode> [sec] [length] [round/rounds]` (fake event data: `name`, `round`, `start`, `run`, `pause`,
  `over`, `off`; BCP is not contacted while active), `bcpfail on|off` (simulated BCP connection errors),
  `portal` (reboot into the captive portal), `reboot`.
- Helpers in `tools/`: run `~/.platformio/penv/bin/python tools/devmon.py` in the background (keeps the port
  open so the device is not reset, logs to `.pio/dev.log`, reads commands from `.pio/dev.fifo`), then
  `tools/devcmd.sh <command>` sends a command and prints the response. Stop devmon before flashing.
- The config web server (started by `mid`) is reachable from the Mac over WiFi at the device IP
  (see `status`), so config changes can be made via HTTP.
- `reset.py` (gitignored) defines a custom `reset` target via esptool; it is not wired into
  `platformio.ini` (`extra_scripts`).
- Tests (PlatformIO Unity): `test/native/` runs on the Mac (env `native`, Arduino `String` from
  ArduinoFake, only `lib/core` and `lib/webui` are compiled), `test/device/` runs on the TC001. Device
  tests replace the firmware: stop devmon before, flash production (or dev) again right after every run
  (the test firmware leaves the display frozen). The TC001 whistles from power-on until firmware drives
  the buzzer pin, so every device test `setup()` must start with `pinMode(15, INPUT_PULLDOWN)`. Running both
  device suites in one `pio test` call sometimes fails to upload the second one; run it again with
  `-f device/<suite>`. Unity on the ESP32 has no 64-bit asserts. Logic that needs tests belongs to
  `lib/core` (no ESP-only includes). Display, WiFi, portal, config server and buttons are verified on the
  device with the dev console.
- Git pre-commit hook `tools/git-hooks/pre-commit` (enable per clone: `git config core.hooksPath tools/git-hooks`):
  native tests always; TC001 suites only for related staged files (`lib/gfx/` → `test_gfx`; `lib/config/`,
  `lib/core/bcpparse.*`, `lib/core/textutil.*` → `test_platform`; `platformio.ini` → both), with upload
  retries, then production is flashed back. Blocks the commit if the TC001 is needed but missing or devmon
  holds the port; `SKIP_DEVICE_TESTS=1 git commit` skips the device part. A commit with device tests takes
  several minutes: run it in the background (Bash timeout is 10 min). Logs in `.pio/precommit/`.
- Claude may flash the device and read its serial output. USB is reliable when the TC001 is plugged
  directly into the MacBook, unreliable through a USB hub. If upload/monitor fails, suspect the hub first.
- In 2025 the device occasionally froze after flashing. Recovery: hold Left + Right to power off, power on
  again, flash again.

## Layout

PlatformIO's LDF picks up each folder in `lib/` as a library; headers are included as `<name.h>`.

| Path | Purpose |
|---|---|
| `src/main.cpp` | `setup()`/`loop()`: data refresh every 60 s, display state decisions (`updateDisplay()`), reboot after 5 consecutive fetch failures, mDNS `<hostname>.local` |
| `src/devconsole.*` | Serial command console, dev build only |
| `tools/` | Mac-side dev helpers: `devmon.py` (persistent serial monitor), `devcmd.sh` (send console command), `bcp_contract.py` (live BCP API contract test, `--dump` saves responses), `git-hooks/pre-commit` (runs the tests) |
| `test/native/`, `test/device/` | Unit tests on the Mac / on the TC001 |
| `lib/bcp/` | `CBCPEvent` singleton `BCPEvent`: calls BCP REST API, keeps event data, RTC snapshot |
| `lib/core/` | Hardware independent logic, unit tested on the Mac: event ID / JSON / time parsing (`bcpparse`), countdown text + colour and round indicator layout (`countdown`), display / refresh decisions and message prefixes (`policy`), `DisplayState` (`displaystate.h`), snapshot validation, string helpers (`textutil`) |
| `lib/hw/hw.h` | Abstract `Hw` interface (static volatile `displayState`, `enforceUpdate`, `redrawRequested`) |
| `lib/hw/tc001.*` | `Tc001` singleton: the TC001 implementation (matrix, buttons, display task, fonts) |
| `lib/config/` | `CConfig` singleton `Config`: settings in NVS + on-demand HTTP config server |
| `lib/wifimgr/` | `CWifiMgr` global `WifiMgr`: multi-network WiFi manager with captive portal, NTP + RTC time sync |
| `lib/devlog/devlog.h` | `DEV_LOG` debug macro, dev build only |
| `lib/webui/` | Shared look of the web pages (captive portal, config page): page template, common CSS, `escapeHtml` |
| `lib/gfx/` | Adafruit_GFX helpers: `ScrollingText`, `ProgressIndicator`, `UTF8canvas16`, fonts |
| `lib/*/*.html`, `wifimgr.css` | Gitignored, formatted copies of the generated pages used for styling, older than `lib/webui`; the real HTML/CSS is inlined as strings in the `.cpp` files |

## Runtime architecture

### Two execution contexts
- **Arduino `loop()`** (main task, core 1 = `CONFIG_ARDUINO_RUNNING_CORE`): config change handling, data refresh, `updateDisplay()`, `delay(10)`.
- **`Tc001::handleEvents`** FreeRTOS task (`xTaskCreatePinnedToCore`, core 1, priority 1, 8 KB stack),
  runs every 10 ms: mid-button handling, `Config.handleClient()`, scrolling text / progress indicator
  steps, and redrawing the countdown when `displayState == DISPLAY_EVENT_COUNTDOWN` (once per second,
  when `time(nullptr)` changes; the dev console `status` shows the redraw count).
- Both contexts draw to the same `FastLED_NeoMatrix` and share `scrollingText`/`progressIndicator`.
  All display access in `tc001.cpp` goes through a recursive mutex (`DisplayLock`); keep new drawing
  code inside it and keep slow work (HTTP, config server) outside.
- Both tasks run on core 1 with the same priority, so FreeRTOS time-slices them; a blocking HTTPS
  request in `loop()` does not stop the countdown redraw (measured 1 redraw/s during fetches). Core 0
  is left to the WiFi stack on purpose: the display task next to it risks FastLED flicker.

### Display state machine (`DisplayState` in `lib/core/displaystate.h`)
`displayState` says what is shown. Only the `Hw` implementation sets it (each `display*()` /
`showSplashScreen()` / `showConfigServerMsg()` method sets its state); `main.cpp` only reads it to skip
redrawing what is already shown.
- `BOOT` — splash screen or connection messages (also while the event ID is not verified yet).
- `EVENT_NAME` — event not running (not started or ended): scrolling event name.
- `EVENT_ROUND` — event running, no timer for the current round: "Round N".
- `EVENT_COUNTDOWN` — timer active; `handleEvents` redraws every second. Colours: green = time to round
  start, white = running, yellow/red = below configured thresholds, blinking magenta = paused.
  Bottom row shows round progress (`displayRoundWithCountdown`). When the remaining time crosses
  the yellow / red threshold between two redraws, `drawCountdown` starts a beep (see Buzzer below).
- `CONFIG_REQUIRED` — invalid event ID: red message once, then the config page address loops; config
  server runs with no timeout.
- `CONFIG_MESSAGE` — config server started by the Mid button: the address scrolls once, data refreshes
  do not redraw meanwhile; when it finishes, `handleEvents` sets `Hw::redrawRequested` and `loop()`
  calls `updateDisplay()` without fetching data.

### Buttons (TC001 pins)
- Mid (GPIO 27): held at boot → force WiFi captive portal; pressed at runtime → start config server (5 min timeout).
- Right (GPIO 14): immediate data refresh (`Hw::enforceUpdate`).
- Left button is not used. LED matrix data on GPIO 32.

### Buzzer (GPIO 15, passive)
- Idles as `INPUT_PULLDOWN`; a floating pin whistles. A beep attaches LEDC channel 0 (`ledcWriteTone`, 2 kHz) and
  pulls the pin down again when the pattern ends.
- `Tc001::stepBeep()` runs in `handleEvents` every 10 ms, so the beep never blocks the countdown. Patterns and
  threshold crossing are in `lib/core/countdown` (`detectThresholdCrossing`, `isBeepOn`): yellow = one 2 s beep,
  red = three 2 s beeps with 1 s gaps. `lastRemaining` is reset in `displayCountdown()`, so the first redraw
  (boot or return from the config message in the middle of a round) never beeps. Disabled by config `beep`.

### Startup flow
`Tc001` ctor (matrix, task) → splash → `WifiMgr.connect()` (blocking; portal if no known/open network
connects or NTP fails) → `BCPEvent.setID(Config.eventId())`. An invalid/empty event ID starts the config
server with no timeout and scrolls "Config page http://<IP>".

### BCP API
- `GET https://newprod-api.bestcoastpairings.com/v2/events/<id>` → `name`, `status.started/ended/numberOfRounds/currentRound`.
  The response is ~6 KB; `parseOverview` uses an ArduinoJson filter to keep only `name` and `status`.
  Spec: https://github.com/honzaskypala/bcp-api/blob/main/bcp-api.yaml
- `GET .../v1/events/<id>/timer?round=<n>` (no v2 exists) → `timerLength`, `startTime`, `endTime` (UTC ISO), `timerPaused`, `pausedTimeRemaining`.
  A round without a timer (also a non-existent round) returns `200 {}`, not 404. BCP has no way to cancel a started timer.
- Header `client-id: web-app`; TLS without cert validation (`setInsecure()`). Unofficial API.
- Responses are parsed directly from the HTTP stream (`parseOverview`/`parseTimer` `Stream&` overloads), no body
  `String`. The request is HTTP/1.0 (`useHTTP10`), so the body is never chunked (BCP sends `Content-Length`).
- 404 on the event (v2) = invalid event ID (counts as a "successful" fetch, not a failure).

### Persistent storage (NVS / Preferences)
- Namespace `config`: `event` (string, ID or URL as entered), `yellow`, `red` (long seconds; legacy string `m:ss` is still read), `beep` (bool, acoustic signals, default on), `hostname`.
- Namespace `wificreds`: `__ssids` (newline-separated list), `pwd_<fnv1a32(ssid) hex>` per network.
- Config web form (`/`, `POST /config`, `/wifi/delete`, `/wifi/deleteAll`) also lists/deletes stored WiFi networks.

### Time
Countdown = `roundEndEpoch - time(nullptr)`, so the system clock must be valid UTC. `WifiMgr` syncs NTP
(`pool.ntp.org`) after each connection and writes it to the DS1307-compatible RTC; if NTP fails, a
plausible RTC time is used instead, otherwise the connection attempt counts as failed.

## Non-obvious contracts

- **`Tc001` is a `Print`** passed to `WifiMgr.connect()` as the user-message sink. `Tc001::write()` buffers
  lines and dispatches on the line prefix (`classifyMessage()` in `lib/core/policy`): `"Error:"` → red scrolling text, `"Connecting "` → "Connect" +
  progress indicator, `"Connected "` → ignored, anything else → white scrolling text. Changing message
  texts in `wifimgr.cpp` changes what the display does.
- **Fonts** (`lib/gfx`):
  - `UTF8_32BitFont` extends `GFXfont` with 32-bit `dFirst/dLast`. `F3x5[]` is a *segmented* font: an
    array of segments (ASCII, Latin-1 + Latin Extended-A, Cyrillic, punctuation, arrows, regional indicators)
    terminated by an all-null entry. Code walking segments relies on that terminator.
  - Time fonts `F4x6` (mm:ss) and `F3x5_Fixed` (h:mm:ss) only cover `-` to `:`; the `/` glyph is an `X`
    bitmap, used to display overflow (`-//://`).
  - Adafruit's `getTextBounds` clips to the display, so `ScrollingText` has its own `measureText`/`measureChar`.
- Singletons: `CBCPEvent`/`CConfig` use private ctor + friend `get...Instance()` + global reference
  (`BCPEvent`, `Config`); `Tc001::getInstance()`; `WifiMgr` is a plain global object.

## Code style

- File header: one-line description, `// (c) 2025 Honza Skýpala`, `// WTFPL license applies`.
- Classes `CName` for singletons, members with trailing underscore (`name_`), methods camelCase.
  (wifimgr/config have some older `_prefix` members.)
- Function and method names start with a verb (`updateDisplay()`, `sealSnapshot()`, `startProgress()`).
  Getters follow the Qt style: value getters are nouns (`name()`, `eventId()`), bool getters use
  `is`/`has` (`isStarted()`, `hasTimeSyncFailed()`). `xToY()` conversions are fine (`secondsToTime()`).
  Overrides of Arduino/Adafruit methods keep their names (`write`, `setFont`, `draw`).
- Per-module debug macros (`MAIN_DEBUG`, `CONFIG_DEBUG`, `WIFIMGR_DEBUG`) are aliases of `DEV_LOG("Module", msg)`,
  which prints `[Module] msg` to `Serial` in the dev build only.
- Arduino `String` is used widely; the TODO lists moving to `const String&` / `char*` where it makes sense.
- Section comments in the form `// ---- Section ----`.

## Planned: Ulanzi TC002 support

Goal: one repository for several target devices. Nothing is implemented yet and we do not have the device.
Findings from https://github.com/atomicstack/tc002-customisation (beta, based on a single unit; items
marked *unverified* came only from a summary of its README). Researched 2026-11.

### Hardware
- **Not an ESP32.** Linux 4.9.84 (OpenWrt GCC 9.1.0 toolchain) on a SigmaStar SSD210 ("Pioneer3"), 2× Cortex-A7
  at 1.0 GHz, 64 MB DRAM in package (~35 MB free for Linux), 32 MiB SPI NOR. Vendor SDK FlyThings/zkswe
  (Windows-only C++ IDE); the stock app runs as the init service `zkswe`. Arduino, ESP-IDF and PlatformIO
  do not apply, so this means a userspace Linux application, not a firmware port.
- **Display:** 52×16 RGB LED matrix driven by a separate pixel MCU. Frames go over `/dev/spidev0.0`, SPI mode 0,
  8 bit, 10 MHz. One frame is 3072 bytes: 16 rows × 192 bytes (52 px × RGB + 36 zero bytes). The latch on GPIO 35
  idles high and is required (plain SPI writes do nothing): drive it low, write the frame, drive it high. The MCU is
  double-buffered, so a frame shows one frame late. `/dev/ttyS1` (UART to the MCU) carries gain, mic, battery
  and power commands and is not needed for pixels.
- **Input:** 3 buttons on top (left, mid, right) plus a rotary encoder `BRI&VOL` with a push button. *Unverified*:
  keys are polled GPIO 31–34 (31 = knob push, 32 left, 33 mid, 34 right), the knob is on GPIO 10/11, and
  device tree names do not match positions. Reset key on GPIO 2 (hold for 5 s = recovery).
- **No RTC** (no driver built in): the clock starts at 1970 on boot and comes only from SNTP. No buzzer, light sensor
  or temperature sensor reported. It has a speaker (*unverified*: amp enable on GPIO 9), a mic read through the MCU,
  and a battery of 3.7 V / 3600 mAh.
- **WiFi:** AIC8800DC over SDIO and managed by the OS, so `lib/wifimgr` and NTP code mostly do not apply.

### Access, storage, risks
- adb with a root shell over USB and over WiFi (port 5555), vid:pid `18d1:d002`. On a factory-fresh unit USB boots
  in host mode; switch it with `echo usb_device > /sys/bus/platform/devices/soc:usbotg/otg_role` and do not read the
  neighbouring `usb_*` sysfs files. Serial pads `GND RX TX` are unpopulated (likely `ttyS0` 115200, untested).
- Persistent writable storage is only `/data` (JFFS2, 8 MB). rootfs (squashfs 3.5 MB) and `/res` (mtd3) are
  read-only, and `/mnt/storage` holds the vendor `update.img`.
- Brick risk: kernel (mtd1) and rootfs writes have no fallback. The `res` image differs between units, so keep
  a verified `mtd3` backup before any write. Running a vendor upgrade with the default directory can install an
  older `update.img`. Whether boot verifies signatures is unknown. Stay in `/data` as long as possible.

### What carries over from this project
- `lib/core`: logic is reusable. It depends only on Arduino `String` and ArduinoJson; it needs `std::string`/`char*`
  or a small `String` shim (ArduinoFake is a test mock, not for production).
- `lib/gfx`: Adafruit_GFX is plain C++ and builds with an Arduino shim; fonts and `ScrollingText` are reusable.
- `Hw` interface (`lib/hw/hw.h`): a new implementation renders to a 52×16 framebuffer, then SPI + latch, using a
  thread instead of a FreeRTOS task. It needs a new layout (the TC001 code is tied to 32×8).
- To be replaced: `lib/bcp` HTTP (`WiFiClientSecure`/`HTTPClient` → libcurl or mbedTLS), `lib/config` storage
  (NVS → file in `/data`) and its web server (the `lib/webui` HTML stays), `setup()`/`loop()` → `main()`.
  Missing abstractions: HTTP fetch, settings storage, config server.
- TC002-only features must be gated per platform so they do not grow the TC001 flash usage.

### Open issues / first steps
1. Toolchain: cross-compile for ARMv7 against the device libc (OpenWrt: musl or uClibc?), probably a static binary.
   Build with CMake next to PlatformIO.
2. Stop or replace `zkswe` (it owns SPI/display) and autostart our binary without writing kernel/rootfs.
3. Feasibility test: static hello world via adb, then one frame on SPI. If either fails, the plan is off.
